# v0.2.9：关机完成通知异常与原厂界面恢复

## 用户提供的现象

用户描述：在插件界面确认关机，静置约 30 多秒后长按电源键，出现原厂“关机中”，随后熄屏；再次长按只有背光，没有界面。

本地查看用户提供的约 112 秒录像，抽帧确认以下画面。时间为录像内时间，不是设备内部事件时间：

| 时间 | 可见画面 |
| --- | --- |
| 约 20 秒 | 插件的“确认关机”页面 |
| 约 22–66 秒 | 未见屏幕界面 |
| 约 68 秒 | 原厂“关机中…”文字 |
| 约 70 秒 | 蓝色 ZTE 标志 |
| 约 72–74 秒 | 标志收缩，随后屏幕变暗 |
| 后续至录像末尾 | 没有恢复可见的操作界面 |

录像证明原厂关机动画出现，不能证明 Linux 是否重启、MC 电源状态为何、插件何时退出，也不能据此宣布是正常待机。原视频包含其他界面信息，仅在电脑本地分析，不随源码或插件分发。

故障设备本轮无法连接。此前通过 SSH 读到的是另一台 TopFlow，用户已明确纠正；该设备的运行时间、电源模式、快速开机设置及插件文件状态全部排除，不能用于判断这次故障。未对任何设备执行安装、切换、开关机、写文件或修改配置。

## 已复现的代码问题

v0.2.8 的原厂完成通知使用与显示控制命令相同的 ACK 失败语义：`device_complete()` 的查找或 RPC 错误使 helper 发送失败 ACK 并退出；父程序把它标为整个通道故障，`runtime_factory_keep_dark()` 返回失败，主循环退出，监管程序随后恢复原厂 UI。

电脑测试使用实际 helper、client、持续熄屏函数及隔离的监管恢复函数，注入完成 RPC 错误后复现上述路径。对照组完成 RPC 成功时继续运行。它证明这是可到达的条件缺陷，**不证明录像中的设备就是因该错误退出**。

## 修正范围

- 完成通知使用独立结果：已确认、未确认、已过期。未确认不等于通道损坏，也不表示设备已经关机。
- 原厂明确 OFF 后，完成通知的业务错误或等待超时不再直接导致屏幕程序退出、重新启动原厂 UI。黑屏、输入门禁和现有监管心跳继续保留。
- 同一 OFF 周期，每类完成 RPC 至多发出一次，不因超时自动补发。查找过程中收到 ON 或更新阶段通知后，旧事件不能继续提交；尚未发出的新阶段需求保留，须重新确认实际熄屏。
- 父程序只允许消费已明确超时的那条完成通知的迟到结果，记录有固定上限。不容忍任意旧序号、重复回执、错误报文或断连。
- 查询 MC 对象使用短命、只读的独立连接，父程序限制等待并回收子进程；该子进程不发完成 RPC、不保留原有 provider 或父子通道。完成 RPC 仍有独立时限，无新增常驻程序或持续日志。
- 不改关机/重启请求，不注册新的 MC 关机参与者，不写原厂电源状态。真正的通信断连、显示事务失败等仍保留原有恢复路径，不能冒充本次修复已覆盖所有电源故障。

## 按键与开机边界

`key_input.c` 以只读方式打开 evdev，不使用 `EVIOCGRAB`，不修改全局按键状态。关机分支只清空插件自身的输入队列和手势状态；原厂仍能接收实体电源键。

电脑按键测试覆盖关机期间丢弃旧按住/松开、重新开机后的新长按、重复事件及队列失步恢复。没有证据支持通过新增独占按键来修复该问题，因此没有加入会影响原厂开机的屏蔽操作。

本地原厂 SDK 证据中，MC `mode_power_on` 对应 UI 开机事件；`POWER_ON_QUICKEN` 是休眠库内部状态标签，不等同于一个已验证的 `mode_power_on_quicken` 广播。背光变亮、普通 WAKE、短按或长按本身都不能代替 MC 开机确认。本版不因这些条件强行解除 OFF 锁存。

## 验证与升级

`native/test-device-power-events.ps1` 增加实际 helper/client 的完成错误、过期事件、迟到结果和真实协议故障测试，避免原测试以简化命令桩跳过 ACK/FATAL 扩大链。相关私有协议、按键、显示和休眠回归仍执行。

管理器增加 v0.2.8 已发布归档的精确迁移清单，保留原有恢复、壁纸迁移与卸载保护。更换 TXT 后必须再更新设备端组件；旧原生程序不会因网页版本变化而自动替换。

本版仍为 `DEVICE_ACCEPTANCE_PENDING`、`hardwareVerified=false`。故障机离线，尚未验证其长按开机、完整关机/重启或再次唤醒。已发现的代码缺陷与本次实机症状之间的因果关系，需要对应设备的退出记录和电源状态才能确认。

还有明确的剩余边界：若 MC 服务在查找时暂不可用，本周期完成通知可能根本没有送达。此时保留“未确认”，不反复尝试，不代替原厂推进电源状态；后续取决于原厂自身的超时和恢复逻辑。用户补充必须强制重启才能恢复，这一实际故障不能仅凭本地回归通过就宣布解决。当前异常未确认消除前，可在设备恢复正常后通过 UFI 切回原厂屏幕使用。
